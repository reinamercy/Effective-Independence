## 2026-08-11 — Phase 1 harness build (api_client, config_runner, graders, cost tracking)

- **Decision:** Cache key = sha256 of `{model_id, system_prompt, user_prompt, temperature, seed}` as sorted JSON; cache entries stored as one JSON file per key under `cache/responses/`.
  **Why:** Simple, inspectable, trivially resumable — rerunning any script only issues calls for keys not already on disk (verified via smoke test: identical call args produce a cache hit with zero cost on the second call).
  **Alternative considered:** SQLite-backed cache — rejected as unnecessary complexity for a project our per-cell volume (~9600 max).

- **Decision:** `get_response()` never raises past its own boundary — provider exceptions are caught after retries are exhausted, logged via `logging_utils.log_error` + `log_call`, and returned as `{"error": ..., "text": None, ...}`. `config_runner.generate()` likewise catches any unexpected exception per-task and emits a null row instead of crashing the batch.
  **Why:** Master spec engineering rule: "fail quiet on infrastructure" — a single malformed API response or transient provider error must not kill a multi-hour batch run. Distinguished from grader failures (e.g. missing `math_verify` import), which are left to raise/crash — those are "fail loud on data quality" per the same rule, since a silently-broken grader would corrupt the whole error matrix.
  **Alternative considered:** Swallowing grader import errors too — rejected, would risk silently marking a whole dataset as 0% correct if a dependency were missing.

- **Decision:** Rate limiting implemented as an in-process sliding-window limiter per provider (`RateLimiter` in `api_client.py`), with `rate_limit_rpm` placeholders (50) in `config/models.yaml` pending real tier limits.
  **Why:** Simple and sufficient for a single-process, single-machine research harness; no need for a distributed limiter.
  **Alternative considered:** N/A. Owner should confirm actual per-provider RPM limits before the Phase 1 pilot run so this isn't overly conservative or gets 429'd.

- **Decision:** SimpleQA LLM-judge fallback defaults to no-op (`correct=False`, audit record still written) unless a `judge_config` is explicitly passed to `grade()`.
  **Why:** Forces the pilot script to make an explicit, visible choice of judge model rather than silently defaulting to one; keeps judge cost attribution explicit in the cost tracker.

- **Not yet built:** dataset acquisition/processing (`data/raw`, `data/processed`), the concrete 12-config definitions (personas, temperatures, model assignments), and `scripts/run_pilot.py` logic. These are next, and require picking specific dataset sources (e.g. GPQA-Diamond, Hendrycks MATH levels 4-5, OpenAI's SimpleQA eval set) — flagged here rather than silently decided, though dataset *source* choice was not gated the way the model list was.

## 2026-08-11 — Live credential verification before the real pilot

- **Finding:** `requests`/`httpx` (and everything built on them: `openai` SDK, `google-genai` SDK, `huggingface_hub`) failed `CERTIFICATE_VERIFY_FAILED` on this network for every provider, while `urllib` succeeded on the same hosts. Root cause: this network does TLS interception with a corporate root CA that's trusted by the Windows OS certificate store (which `urllib` uses by default on Windows) but absent from `certifi`'s public CA bundle (which `requests`/`httpx` use by default).
  **Fix:** added `src/utils/ssl_bootstrap.py`, which calls `truststore.inject_into_ssl()` to make `ssl.create_default_context()` — and therefore every library built on it — use the OS trust store instead of certifi. Imported at the top of `api_client.py` and `dataset_loader.py`, the two modules that make network calls.
  **Why not just point `REQUESTS_CA_BUNDLE` at a exported cert file:** `truststore` is the standard, low-maintenance fix for exactly this OS-trust-store-vs-certifi mismatch and needs no manual cert export/rotation.
  **Verified:** after the fix, real (non-mocked) calls succeeded against Google (Gemini), OpenRouter, and HuggingFace, and a real `api_client.get_response()` round-trip confirmed cache hit/miss behavior works against a live API, not just mocks.

- **Finding:** live 429 errors from Gemini revealed the *actual* free-tier quota on this project: **RPM=5, RPD=20, per model** (not the 250-1500/day the public pricing pages reported in an earlier web search). Confirmed by parsing the error's `quotaId` field: `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` (value 5) and `GenerateRequestsPerDayPerProjectPerModel-FreeTier` (value 20).
  **Why this matters:** `mid_tier_model` (gemini-3.5-flash) is deliberately shared across 8 of the 12 configs (prompt_diverse x3, temperature_diverse x3, size_diverse_medium, family_diverse_0) per the axis design in project_spec.yaml — that's inherent to the axis definitions, not a mistake. At 20/day for that one model, the already-shrunk 150-question full run would have taken ~60 days (8 configs x 150 questions / 20 per day), blowing the 6-week deadline.
  **Decision (owner chose "shrink further + spread over many days" over paying or switching providers):** cut `total_questions_target` 150 -> 30 (GPQA 40->8, MATH 55->11, SimpleQA 55->11) and the pilot ~21 -> ~9 (3/dataset). At 30 total, the gemini-3.5-flash-bottlenecked portion is 8 configs x 30 = 240 calls / 20 per day ~= 12 days -- fits inside the 6-week deadline with room for analysis/writing.
  **Verified cache-compatible:** because each loader shuffles the *full* downloaded set once with a fixed seed (0) and then takes a prefix (`items[:target_n]`), shrinking `target_n` doesn't reshuffle -- the smaller set is a strict prefix of the larger one, so already-cached API responses for those questions are still reused (confirmed: `gpqa_diamond_0`'s ground truth was identical, 'D', before and after the shrink from 40->8).

- **Fix:** `api_client.py`'s rate limiter was keyed by provider only, so Gemini's shared "google" limiter would throttle e.g. `gemini-3.5-flash-lite` calls based on `gemini-3.5-flash`'s traffic even though they have independent quotas. Changed `_get_rate_limiter` to key by `(provider, model_id)`. Also set `rate_limit_rpm: 5` for google (previously an unconfirmed placeholder of 10) to match the confirmed real limit.

- **Fix (efficiency):** a daily-quota-exhausted call was retrying up to 5x with exponential backoff (~2-4 minutes wasted per call) even though retrying within the same day can never succeed -- Gemini's error message distinguishes per-minute (`...PerMinute...`, retry-worthy) from per-day (`...PerDay...`, not retry-worthy) quota violations. Added `DailyQuotaExhaustedError` (not in tenacity's retry condition, so it fails immediately) and `_call_google` now raises it specifically when `PerDay` appears in the error, instead of the generic retry-worthy `RateLimitedError`.

- **Fix (real bug, not quota-related):** `run_pilot.py` crashed with `UnicodeEncodeError` partway through printing the hand-audit sample -- Windows' console defaults stdout to cp1252, and a model response contained U+2011 (non-breaking hyphen). This silently ate the rest of the audit output, the cost dashboard, and the completion/incomplete status message on the run where it happened. Fixed by reconfiguring `sys.stdout`/`sys.stderr` to UTF-8 with `errors="replace"` at the top of the script.

- **Fix (real correctness bug, found via the pilot's actual output):** many pilot responses -- especially from the two reasoning-style OpenRouter models (`openai/gpt-oss-20b:free`, `nvidia/nemotron-3-ultra-550b-a55b:free`) but also plain `gemini-3.5-flash` on verbose MATH problems -- came back truncated or completely empty (`raw_response: ''`), because `max_tokens=1024` wasn't enough once a reasoning model spent its budget on a hidden reasoning trace before any visible output, or a model's step-by-step derivation ran long. This was silently deflating the pilot's accuracy numbers (17.4% correct on the partial pilot) with "no answer given" rather than "wrong answer."
  **Compounding bug:** the cache key (`_cache_key` in `api_client.py`) did NOT include `max_tokens`, so simply raising the config's `max_tokens` would have kept returning the old truncated cached responses forever -- the fix would have silently done nothing.
  **Fix:** added `max_tokens` to the cache key hash, and raised the default in `config_runner.py` from 1024 to 4096. Since this changes the cache key, all previously-cached responses are naturally superseded (not deleted, just orphaned) and will be regenerated fresh on the next run.
  **Cost of this fix:** today's already-spent daily quota on the old (truncated) 1024-token responses is effectively wasted -- those cells need to be regenerated under the new key. No monetary cost (still free tier), but it costs another day or two of the generation timeline. Judged worth it: shipping results with silently-truncated reasoning-model outputs would be a real validity problem in the paper, worse than a short timeline delay.

- **Known unresolved issue (carried over, not yet fixed):** `math_verify`'s internal multiprocessing still throws `OSError: [WinError 6]` noise on this Windows machine during MATH grading (spams stderr but doesn't crash the run, confirmed across multiple pilot runs). Grading correctness under this condition is still unverified — flagged for the project lead to check once a MATH-heavy hand-audit is possible.

- **Process note:** the pilot is now expected to run in **small daily batches** rather than to completion in one sitting, because of the real quota ceiling above. Re-running `python scripts/run_pilot.py` is fully safe to repeat daily (idempotent via the cache) -- it will pick up exactly where the previous day's run left off and report `INCOMPLETE` with a count of quota-exhausted cells until all 108 pilot (question, config) pairs are filled.

- **Fix (real correctness bug, found via the max_tokens-fixed pilot's actual output):** `math_grader.extract_boxed()` used a non-greedy regex (`\\boxed\{(.+?)\}`) that stops at the FIRST closing brace -- MATH answers routinely nest braces (e.g. `\boxed{\frac{6}{7}}`), and the regex was truncating that to `\frac{6}`, silently corrupting extraction for any boxed answer containing `\frac`, `\sqrt`, or similar. Confirmed live: a pilot response with `\boxed{\frac{6}{7}}` extracted as `'\frac{6'`. Rewrote `extract_boxed()` to find the last `\boxed{` and match its closing brace by depth-counting instead of regex, handling arbitrary nesting correctly. Verified against the exact failing case plus simple/unbalanced/multiple-boxed edge cases.
  **Note:** this fix does not require regenerating any cached API responses (only the grading/extraction logic changed, not generation), so it doesn't cost any additional quota -- just needs the pilot's grading step re-run once generation is complete.

## 2026-08-15 — CRITICAL: math_verify was silently marking every MATH answer wrong

- **Finding (caught via manual hand-audit of real pilot output, at the project lead's explicit request to verify a sample):** two MATH examples in the pilot's audit sample showed `extracted_answer` as an EXACT match to the ground truth's boxed value (`\frac{6}{7}` vs `\frac{6}{7}`; `1` vs `1`) yet both were graded `correct=False`. Investigated directly: `math_verify.parse()` was returning `[]` (empty) for every input, including the trivial case `parse("42")`. With `raise_on_error=True`, the real exception surfaced: `AttributeError: Can't pickle local object 'timeout.<locals>.decorator.<locals>.wrapper.<locals>.run_func'`.
  **Root cause:** `math_verify`'s default timeout wrapper (`parsing_timeout=5` on `parse()`, `timeout_seconds=5` on `verify()`) uses `multiprocessing` to enforce the timeout. On Windows (spawn-based process start, unlike Unix's signal-based `SIGALRM` approach that `math_verify` uses instead when `os.name == "posix"`), spawning a subprocess requires pickling the target function -- but the timeout decorator's target is a locally-defined nested closure, which cannot be pickled. This raised on every single call. Because `math_verify`'s default is `raise_on_error=False`, this failure was being silently swallowed and both `parse()` and `verify()` returned empty/`False` unconditionally, with **zero indication of a problem** other than suspiciously low MATH accuracy.
  **Impact:** every MATH grading result produced by this project before this fix was wrong -- every MATH question was being scored as incorrect regardless of the model's actual answer. This was not caught by earlier automated testing because the earlier `math_grader.py` unit tests (brace-matching fix, logged above) tested `extract_boxed()` in isolation, not the full `grade()` path through `math_verify`. **This is exactly why manual hand-audit of real output matters and automated tests alone aren't suffient** -- confirmed by the project lead explicitly asking to verify a sample rather than just trusting the summary numbers.
  **Fix:** pass `parsing_timeout=0` to `parse()` and `timeout_seconds=0` to `verify()` in `math_grader.py`'s `grade()`. Per `math_verify`'s own source (`utils.py`): `if timeout_seconds is None or timeout_seconds <= 0: return no_timeout_decorator` -- this skips the broken multiprocessing path entirely and falls back to synchronous parsing, which works correctly.
